# Smart ITSM RESTful API 接口设计文档

**项目名称：** Smart ITSM 智能 IT 服务管理系统

**文档版本：** V1.0

**接口风格：** RESTful API

**基础路径：** `/api/v1`

**数据库：** MySQL 8.0

**后端技术栈：** Java 17 + Spring Boot + MyBatis-Plus + Spring Security + Redis + RabbitMQ

**整体技术架构：**

```
                 Smart ITSM
                        │
              ┌─────────┴─────────┐
              │                   │
          RESTful API          Spring Security
              │                   │
              └─────────┬─────────┘
                        ↓
                 Spring Boot
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      Service        Redis        RabbitMQ
          │             │             │
          ↓             │        异步业务处理
     MyBatis-Plus       │
          │             │
          └──────┬──────┘
                 ↓
               MySQL
```

**认证方式：** JWT

**字符编码：** UTF-8

**数据格式：** `application/json`


---

# 1. 文档概述

## 1.1 项目简介

Smart ITSM 是面向企业内部 IT 服务场景设计的工单管理系统。

系统主要解决企业员工在使用计算机、网络、软件、硬件以及信息安全服务过程中产生的问题，通过统一的工单流程完成：

> 用户提交问题 → 团队负责人分配 → 工程师接受 → 工程师处理 → 必要时协作 → 提交解决方案 → 用户确认 → 工单关闭

系统同时提供 SLA 管理、消息通知、工单历史、附件、知识库以及 AI 异步任务等能力。

---

# 2. 用户角色

系统目前设计四类业务角色。

| 角色编码      | 角色名称   | 核心职责                                               |
| --------------- | ------------ | -------------------------------------------------------- |
| USER          | 普通用户   | 创建和查看自己的工单、评论、附件、催办、确认解决       |
| ENGINEER      | 工程师     | 接受和处理分配的工单、转派、协作、提交解决方案         |
| TEAM\_MANAGER | 团队负责人 | 查看团队工单、分配/重新分配工单、处理 SLA 和团队统计   |
| ADMIN         | 系统管理员 | 用户、角色、权限、部门、团队、分类、SLA 和系统配置管理 |

一个用户可以同时拥有多个角色。

例如：

```text
王主管
USER
ENGINEER
TEAM_MANAGER
```

因此权限判断应基于​**权限编码**​，而不是简单判断用户是否属于某一个角色。

# 3. API 基础规范

## 3.1 URL 规范

统一使用：

```text
/api/v1/{resource}
```

例如：

```text
GET    /api/v1/tickets
POST   /api/v1/tickets
GET    /api/v1/tickets/{ticketId}
POST   /api/v1/tickets/{ticketId}/assign
POST   /api/v1/tickets/{ticketId}/accept
POST   /api/v1/tickets/{ticketId}/resolve
```

不建议设计：

```text
POST /api/v1/updateTicketStatus
POST /api/v1/doAssignTicket
```

业务动作通过资源子路径表达。

---

# 4. HTTP 方法规范

| 方法   | 用途                   |
| -------- | ------------------------ |
| GET    | 查询资源               |
| POST   | 创建资源或执行业务动作 |
| PUT    | 完整更新资源           |
| PATCH  | 局部更新资源           |
| DELETE | 删除资源               |

对于工单状态变化，不允许使用：

```text
PUT /tickets/{id}
{
    "status": "CLOSED"
}
```

而应该使用：

```text
POST /tickets/{id}/confirm
```

由后端根据当前状态、操作人身份、权限和业务条件判断是否允许：

```text
WAITING_CONFIRM → CLOSED
```

# 13. 工单状态定义

系统只保留以下 7 个核心状态：

| 状态                   | 含义   |
| ------------------------ | -------- |
| OPEN                   | 待分配 |
| ASSIGNED               | 待接受 |
| PROCESSING             | 处理中 |
| WAITING\_COLLABORATION | 协作中 |
| WAITING\_CONFIRM       | 待确认 |
| CLOSED                 | 已关闭 |
| CANCELLED              | 已取消 |

---

# 14. 工单状态机

完整流程：

```text
┌────────────────────┐
                 │                    ↓
OPEN ──分配──> ASSIGNED ──接受──> PROCESSING
                                      │
                                      │ 发起协作
                                      ↓
                           WAITING_COLLABORATION
                                      │
                                      │ 协作完成
                                      ↓
                                  PROCESSING
                                      │
                                      │ 提交解决方案
                                      ↓
                              WAITING_CONFIRM
                               │            │
                         拒绝解决        确认解决
                               │            │
                               ↓            ↓
                           PROCESSING      CLOSED
```

取消：

```text
OPEN ───────────────→ CANCELLED
ASSIGNED ───────────→ CANCELLED
PROCESSING ─────────→ CANCELLED
WAITING_COLLABORATION → CANCELLED
```

`CLOSED` 和 `CANCELLED` 为终态。

---

# 15. 状态流转原则

禁止客户端直接提交：

```json
{
  "status": "CLOSED"
}
```

客户端只能调用业务动作：

```text
/assign
/accept
/transfer
/collaborations
/resolve
/confirm
/reject
/cancel
```

Service 层统一进行状态校验。

例如：

```text
POST /tickets/10001/confirm
```

后端检查：

```text
1. 用户是否登录
2. 用户是否拥有 ticket:confirm
3. 当前工单是否存在
4. 当前用户是否为工单创建人
5. 当前状态是否 WAITING_CONFIRM
6. 执行 CLOSED 状态转换
7. 更新 closed_at
8. 写入 ticket_history
9. 更新 SLA
10. 创建通知
```

整个操作使用事务：

```java
@Transactional
```

# 16. 创建工单

### 接口

```http
POST /api/v1/tickets
```

权限：

```text
ticket:create
```

角色：

```text
USER
ENGINEER
TEAM_MANAGER
ADMIN
```

只要拥有 `ticket:create` 权限即可创建。

### 请求

```json
{
  "title": "无法连接公司内部系统",
  "description": "今天上午开始无法访问公司内部 OA 系统。",
  "categoryId": 10001,
  "priority": "HIGH",
  "teamId": null,
  "attachmentIds": []
```

### 参数

| 参数          | 类型   | 必填 | 说明                   |
| --------------- | -------- | ------ | ------------------------ |

| categoryId    | Long   | 是   | 工单分类               |
| priority      | String | 是   | URGENT/HIGH/MEDIUM/LOW |
| teamId        | Long   | 否   | 指定处理团队           |
| attachmentIds | Long[] | 否   | 附件 ID                |

```text
ticketNo
creatorId
departmentId
status
createdAt
updatedAt
```

初始状态：

```text
OPEN
```

### 返回

```json
{
  "id": 100001,
  "ticketNo": "IT202609090001",
  "status": "OPEN",
  "statusName": "待分配"
```

# 22. 处理工单

```http
POST /api/v1/tickets/{ticketId}/process
```

权限：

```text
ticket:process
```

该接口用于记录工程师处理过程。

请求：

```json
{
  "content": "已检查用户账号状态，目前发现账号权限配置异常。"
}
```

该动作不会产生新的核心状态。

如果当前已经：

```text
PROCESSING
```

则继续保持：

```text
PROCESSING
```

同时创建：

```text
ticket_comment
```

并记录：

```text
ticket_history.action = PROCESS
```

这样可以避免为了“处理一下工单”而增加大量无意义状态。

# 27. 提交解决方案

```http
POST /api/v1/tickets/{ticketId}/resolve
```

权限：

```text
ticket:resolve
```

状态要求：

```text
PROCESSING
```

请求：

```json
{
  "resolution": "已重新配置用户账号权限，并验证 OA 系统可以正常访问。",
  "remark": "问题已经解决，请用户确认。"
}
```

### 状态

```text
PROCESSING → WAITING_CONFIRM
```

更新：

```text
ticket.resolved_at = now
ticket.updated_at = now
```

同时：

```text
ticket_sla.resolved_at = now
```

这里的 `resolved_at` 表示：

> 工程师已经提交解决方案。

并不表示工单已经关闭。

写入：

```text
ticket_history.action = RESOLVE
```

通知工单创建人。


```json
{
  "reason": "问题已经自行解决，不再需要 IT 支持。"
```

```text

PROCESSING → CANCELLED
WAITING_COLLABORATION → CANCELLED
```

权限根据实际业务控制。

普通用户：

```text
只能取消自己创建且尚未完成的工单
```

管理员：

```text
可以执行系统级取消
```

取消后：

```text
CLOSED
CANCELLED
```

均不可再次流转。

```http
POST /api/v1/tickets/{ticketId}/nudge
```

权限：

```text
ticket:nudge
```

请求：

```json
{
  "message": "该问题影响当前业务，请尽快处理。"
}
```

系统向：

```text
当前工程师
团队负责人
```

发送通知。

催办不会修改：

```text
ticket.status
```

历史：

```text
action = NUDGE
```

如果严格按照当前 `ticket_history.action` 枚举设计，也可以将 `NUDGE` 纳入标准动作集合。

# 40. SLA 升级

权限：

```text
ticket:escalate
```

接口：

```http
POST /api/v1/tickets/{ticketId}/escalate
```

请求：

```json
{
  "reason": "工单超过 SLA 处理时限。"
}
```

升级动作可以：

```text
通知团队负责人
```

并记录：

```text
ticket_history.action = ESCALATE
```

注意：

**SLA 超时不代表自动修改工单状态。**

例如：

```text
PROCESSING
```

即使超时：

```text
PROCESSING
```

仍然可以继续处理。

# 70. 枚举规范

Java 中建议使用：

```java
public enum TicketStatus {

    OPEN,
    ASSIGNED,
    PROCESSING,
    WAITING_COLLABORATION,
    WAITING_CONFIRM,
    CLOSED,
    CANCELLED
}
```

优先级：

```java
public enum TicketPriority {

    URGENT,

    MEDIUM,
    LOW
}
```

不要在 Service 中大量出现：

```java
if ("PROCESSING".equals(status))
```

```java
TicketStatus.PROCESSING
```

# 71. 工单状态机实现规范

建议单独设计：

```text
TicketStateMachine
```

例如：

```java
public void validateTransition(
        TicketStatus current,
        TicketAction action) {

    // 校验当前状态是否允许执行该动作
}
```

动作：

```java
public enum TicketAction {

    CREATE,
    ASSIGN,
    ACCEPT,
    TRANSFER,
    PROCESS,
    COLLABORATE,
    COLLABORATION_COMPLETE,
    RESOLVE,
    REJECT_RESOLUTION,
    CANCEL,
    CLOSE,
    ESCALATE,
    NUDGE
}
```

例如：

```text
OPEN + ASSIGN
        ↓
ASSIGNED
```

```text
ASSIGNED + ACCEPT
        ↓
PROCESSING
```

```text
PROCESSING + RESOLVE
        ↓
WAITING_CONFIRM
```

```text
WAITING_CONFIRM + CONFIRM
        ↓
CLOSED
```

这样可以避免多个 Controller 分别实现状态判断导致逻辑不一致。

# 72. 工单状态变更事务

工单核心操作必须使用事务。

例如：

```text
POST /tickets/{id}/resolve
```

一次业务操作可能涉及：

```text
ticket
ticket_sla
ticket_history
notification
ticket_comment
```

因此应该：

```java
@Transactional(rollbackFor = Exception.class)
```

保证：

> 工单状态修改成功，但历史记录写入失败

这种脏数据情况不会发生。

# 77. 数据权限设计

系统不能只依赖角色权限。

例如：

工程师拥有：

```text
ticket:process
```

并不代表他可以处理任意工单。

还必须判断：

```text
ticket.assignee_id == currentUser.id
```

团队负责人拥有：

```text
ticket:view:team
```

还需要判断：

```text
ticket.team_id ∈ currentUser.managedTeams
```

普通用户拥有：

```text
ticket:view:self
```

则查询条件必须自动增加：

```sql
WHERE creator_id = #{currentUserId}
```

因此最终权限实际上是：

```text
RBAC 权限
+
数据权限
+
业务状态
+
资源归属关系
```

# 80. 当前数据库与接口设计需要注意的问题

## 80.1 工单评价缺少数据表

当前权限中存在：

```text
ticket:rate
```

但是当前数据库没有：

```text
ticket_rating
```

因此评价接口暂时不能真正落地。

如果要实现：

```http
POST /api/v1/tickets/{id}/rating
```

建议新增：

```sql
ticket_rating
```

至少包含：

```text
id
ticket_id
user_id
score
comment
created_at
```

并增加：

```text
UNIQUE(ticket_id, user_id)
```

确保一个用户不能重复评价同一工单。

# 81. ticket\_history 审计能力

当前：

```text
ticket_history
```

已经能够记录：

```text
operator_id
action
from_status
to_status
remark
created_at
```

已经可以满足第一版工单审计需求。

但对于：

```text
ASSIGN
TRANSFER
```

仅记录状态并不能完整描述：

```text
从谁
转给谁
从哪个团队
转到哪个团队
```

V1 可以通过：

```text
remark
```

记录。

例如：

```text
"工单从账号权限组/李娜转交网络运维组/王工"
```

如果后续系统继续扩展，可以给：

```text
ticket_history
```

增加：

```text
metadata JSON
```

保存结构化业务变化。

# 82. 删除策略

对于以下数据：

```text
用户
部门
团队
分类
SLA
知识文档
```

原则上不直接物理删除。

优先使用：

```text
status = DISABLED
status = OFFLINE
```

原因是这些数据可能已经被历史工单引用。

工单本身也不建议物理删除。

工单生命周期结束后：

```text
CLOSED
CANCELLED
```

即可。

# 83. API 安全要求

所有接口必须进行：

```text
认证
↓
权限
↓
数据权限
↓
业务状态
↓
参数校验
```

不能只判断：

```java
if (user.getRole().equals("ADMIN"))
```

应该通过 Spring Security：

```text
Authentication
GrantedAuthority

```

完成权限判断。

# 84. 防止越权

例如用户 A：

```text
ticketId = 10001
creatorId = 用户 B
```

用户 A 即使知道：

```text
GET /api/v1/tickets/10001
```

也不能读取。

Service 层必须进行数据权限检查。

---

# 85. 幂等性

以下接口需要重点考虑重复请求：

```text
assign
accept
resolve
confirm
cancel
```

例如用户连续点击两次：

```text
POST /tickets/10001/confirm
```

第一次：

```text
WAITING_CONFIRM → CLOSED
```

第二次：

```text
CLOSED
```

应该返回：

```text
B0005
工单已关闭
```

而不是再次执行关闭逻辑。

---

# 86. 并发控制

工单属于典型的并发修改资源。

例如：

```text
主管 A
主管 B
```

同时给一个：

```text
OPEN
```

工单分配不同工程师。

因此更新时建议使用：

```text
乐观锁
```

或：

```text
UPDATE ... WHERE id = ? AND status = 'OPEN'
```

确保只有一个请求能够完成状态转换。

如果项目后期增加 `version` 字段，可以采用：

```text
version
```

实现标准乐观锁。

# 87. 缓存策略

不建议缓存：

```text
ticket.status
ticket.assignee
ticket_sla
```

这种强一致性数据。

可以考虑缓存：

```text
ticket_category
sys_department
sys_team
sla_rule
```

因为这些数据读多写少。

Redis 主要用于：

```text
热点配置
分类树
团队信息
用户权限信息
```

工单核心状态仍然以 MySQL 为最终数据源。


```text
用户
                  │
                  │ 创建
                  ↓
              ┌───────┐
              │ OPEN  │
              └───┬───┘
                  │ 分配
                  ↓
             ┌─────────┐

                  │ 接受

                  │
        ┌─────────┴─────────┐
        │                   │

        │                   │
        ↓                   ↓

        │                   │
```

```text
Smart ITSM
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      工单         SLA          权限
        │            │            │
        ↓            ↓            ↓

        │
        ↓

        │
        ↓
        AI
```
